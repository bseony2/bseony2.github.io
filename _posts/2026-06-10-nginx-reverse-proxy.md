## 들어가며

프론트엔드를 Docker 컨테이너로 배포했는데 백엔드 데이터를 하나도 불러오지 못했다. 로컬에서는 잘 됐는데, 서버에 올리니 브라우저에서 CORS 에러가 터졌다.

원인을 파고들다 보니 Nginx 리버스 프록시가 해결책이었다. 이 글에서는 Nginx가 뭔지부터 시작해서 리버스 프록시가 왜 CORS 문제를 해결하는지까지 정리했다.

---

## 1. Nginx란

### 웹서버란

웹서버는 클라이언트(브라우저)의 요청을 받아서 응답을 돌려주는 소프트웨어다.

```
브라우저 → "index.html 줘" → 웹서버 → index.html 반환
```

Apache와 함께 가장 많이 쓰이는 웹서버가 Nginx다. Apache가 요청마다 스레드를 생성하는 방식인 반면, Nginx는 이벤트 기반 비동기 처리 방식이라 동시 접속이 많아도 메모리를 효율적으로 사용한다.

### Nginx가 할 수 있는 일

- **정적 파일 서빙** — HTML, CSS, JS, 이미지 파일을 브라우저에 전달
- **리버스 프록시** — 요청을 다른 서버로 대신 전달
- **로드 밸런싱** — 여러 서버에 요청을 분산

### React 빌드 결과물에 Nginx가 필요한 이유

React 앱은 `npm run build`하면 정적 파일만 생성된다.

```
npm run build
    ↓
dist/
├── index.html
├── assets/main.js
└── assets/style.css
```

이 파일들은 스스로 실행되는 서버 프로세스가 없다. Spring Boot는 내장 톰캣이 있어서 자체적으로 HTTP 요청을 받을 수 있지만, React 빌드 결과물은 누군가 브라우저에 전달해줄 서버가 필요하다. 그게 Nginx다.

로컬 개발 시 `npm run dev`가 되는 건 Vite가 개발용 서버를 내장하고 있기 때문이다. 하지만 운영 환경에는 적합하지 않다.

| | Spring Boot | React |
|---|---|---|
| 실행 | 자체 서버 내장 | 웹서버 필요 |
| 개발 환경 | `./gradlew bootRun` | `npm run dev` (Vite 내장 서버) |
| 운영 환경 | `java -jar app.jar` | Nginx |

## 2. 프록시란

### 프록시 개념

프록시는 **대리자**다. A와 B가 직접 통신하는 대신 중간에 대리인이 끼는 구조다.

```
직접 통신
브라우저 ──────────────── 서버

프록시 사용
브라우저 ──── 프록시 ──── 서버
```

### 포워드 프록시 vs 리버스 프록시

프록시는 누구를 대리하느냐에 따라 두 종류로 나뉜다.

**포워드 프록시 — 클라이언트 뒤에 위치**

```
[클라이언트] → [포워드 프록시] → 인터넷 → [서버]
```

**리버스 프록시 — 서버 앞에 위치**

```
[클라이언트] → 인터넷 → [리버스 프록시] → [서버]
```

이름이 리버스(reverse)인 이유는 포워드 프록시와 방향이 반대이기 때문이다.

| | 포워드 프록시 | 리버스 프록시 |
|---|---|---|
| 위치 | 클라이언트 뒤 | 서버 앞 |
| 대리 대상 | 클라이언트 | 서버 |
| 누가 숨어있나 | 클라이언트 (서버가 IP 모름) | 서버 (클라이언트가 구조 모름) |
| 설정 주체 | 클라이언트 측 | 서버 측 |
| 주요 사용처 | 방화벽, VPN, 사이트 차단 우회 | 웹서버 앞단, 로드밸런서, API 게이트웨이 |
| 대표 사례 | 회사 내부망, Tor 네트워크 | Nginx, Apache, AWS ALB |
| CORS 해결 | 불가 | 가능 (출처 통일) |
| 로드 밸런싱 | 불가 | 가능 |

## 3. CORS란

### 출처(Origin)란

출처는 **프로토콜 + 도메인 + 포트** 세 가지를 합친 개념이다.

```
http://192.168.219.198:80
─────  ────────────────  ──
프로토콜      도메인       포트
```

셋 중 하나라도 다르면 다른 출처다. 경로(`/`, `/api`)는 출처 판단에 영향을 주지 않는다.

```
http://192.168.x.x:80    → 같은 출처
http://192.168.x.x:8080  → 다른 출처 (포트 다름)

http://localhost:3000 → 같은 출처
http://localhost:8080 → 다른 출처 (포트 다름)
```

### 브라우저가 CORS를 막는 이유

브라우저에는 **동일 출처 정책(Same-Origin Policy)** 이라는 보안 정책이 내장돼있다. 악의적인 사이트가 다른 사이트의 API를 몰래 호출하는 걸 막기 위해서다.

```
나쁜 사이트 (evil.com)
    ↓
브라우저에서 은행(bank.com/api)으로 몰래 요청
    ↓
브라우저가 차단 ← 동일 출처 정책
```

브라우저는 다른 출처로 요청할 때 서버한테 "이 요청 허용하냐?"고 물어본다. 서버가 허용한다고 응답하면 통과시키고, 응답이 없으면 차단한다.

```
브라우저 → 백엔드 API 요청
              ↓
백엔드 응답 헤더:
Access-Control-Allow-Origin: http://192.168.x.x
              ↓
브라우저: "서버가 허용했네" → 통과
```

### curl은 왜 통과되나

CORS는 **브라우저의 보안 정책**이다. 서버가 막는 게 아니다. curl은 브라우저가 아니기 때문에 CORS 정책이 적용되지 않는다.

```
curl      → CORS 정책 없음 → 그냥 통과
브라우저  → CORS 정책 있음 → 다른 출처면 차단
```

그래서 curl로 테스트하면 잘 되는데 브라우저에서만 안 되는 상황이 발생한다.

## 4. Nginx 리버스 프록시로 CORS 해결하기

### 포트 포워딩 개념

Nginx 리버스 프록시가 CORS를 해결하는 원리는 간단하다. 브라우저가 보는 포트를 하나로 통일하는 것이다.

```
프록시 없을 때
브라우저(:80) → 프론트
브라우저(:8080) → 백엔드  ← 브라우저가 두 포트를 직접 봄 → 다른 출처

프록시 있을 때
브라우저(:80) → Nginx → 프론트 파일 서빙
브라우저(:80/api) → Nginx → 백엔드(:8080) 포워딩
                    ↑ 브라우저는 80 포트만 봄 → 같은 출처
```

백엔드 8080 포트는 여전히 존재한다. 브라우저가 모를 뿐이다. Nginx가 앞에서 받아서 포워딩하기 때문이다.

### nginx.conf 예제

```nginx
server {
    listen 80;

    location / {
        root /usr/share/nginx/html;
        index index.html;
        try_files $uri $uri/ /index.html;
    }

    location /api {
        proxy_pass http://backend-server:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

핵심은 `proxy_pass` 한 줄이다.

```nginx
proxy_pass http://backend-server:8080;
```

브라우저에서 `/api/...`로 요청이 오면 Nginx가 `http://backend-server:8080/api/...`로 포워딩한다.

`proxy_set_header`는 포워딩할 때 원래 요청자 정보를 백엔드에 전달하는 옵션이다. 없어도 동작하지만, 백엔드에서 클라이언트 IP를 로깅하거나 도메인 기반 분기를 할 때 필요하다.

## 5. Docker 환경에서의 리버스 프록시

### 컨테이너 이름이 호스트명이 되는 원리

Docker 브릿지 네트워크에 연결된 컨테이너끼리는 컨테이너 이름으로 통신할 수 있다. IP 주소 대신 이름을 호스트명으로 사용하는 것이다.

```
finmate-network
├── finmate-frontend  → http://finmate-backend:8080 으로 통신 가능
└── finmate-backend
```

그래서 nginx.conf에서 IP 대신 컨테이너 이름을 쓸 수 있다.

```nginx
proxy_pass http://finmate-backend:8080;
```

### Finmate 구조 정리

```
브라우저
    ↓ http://서버주소/
Nginx 컨테이너 (포트 80)
├── / 요청 → dist/ 정적 파일 서빙
└── /api 요청 → finmate-backend:8080 포워딩
                    ↓
              Spring Boot 컨테이너 (포트 8080)
                    ↓
              PostgreSQL 컨테이너 (포트 5432)
```

브라우저는 Nginx와만 통신한다. 백엔드와 DB는 외부에 노출되지 않고 Docker 네트워크 안에서만 통신한다.

## 마치며

CORS 에러가 처음 나왔을 때는 단순히 백엔드에서 허용 설정을 추가하면 되는 문제라고 생각했다. 하지만 Nginx 리버스 프록시를 적용하니 코드 수정 없이 구조적으로 해결됐다.

리버스 프록시는 CORS 해결 외에도 서버 정보 은닉, 로드 밸런싱, SSL 인증서 통합 관리 등 다양한 이점이 있다. 서버 앞단에 Nginx를 두는 패턴이 실무에서 표준처럼 쓰이는 이유를 직접 경험하면서 이해할 수 있었다.

## 정리

| 항목 | 내용 |
|------|------|
| Nginx | 웹서버. 정적 파일 서빙 + 리버스 프록시 역할 |
| 포워드 프록시 | 클라이언트 뒤에 위치, 클라이언트를 대리 |
| 리버스 프록시 | 서버 앞에 위치, 서버를 대리 |
| CORS | 브라우저의 동일 출처 정책. 포트가 달라도 다른 출처 |
| 해결 원리 | Nginx가 80 포트로 요청을 받아 8080으로 포워딩 → 브라우저는 80 포트만 봄 |
| Docker 환경 | 같은 브릿지 네트워크의 컨테이너 이름을 호스트명으로 사용 |
